1. Visão geral

1.1 Arquitetura

O Iter Store é uma aplicação PHP sem framework externo, com PostgreSQL. Tem duas portas de entrada:

  • Painel administrativo (/admin): telas renderizadas no servidor, sessão por cookie, proteção CSRF (form_key) e permissões por perfil (ACL).
  • API GraphQL (/core/graphql/index): um único endpoint para o app, o site e integrações (ERP, atendimento, contabilidade). O contrato completo fica em schema.graphql, na raiz do projeto.

Os dados flexíveis (atributos de produto, categoria, cliente e endereço) usam o modelo EAV: os campos são criados no painel (Catálogo → Atributos) e aparecem na API em attributes, sem mudar o código. As views customer_flat e customer_address_flat entregam o cliente "achatado" para consultas.

O código fica em módulos (src/vendor/Iter/<Módulo>), cada um com etc/config.json (nome e dependências), etc/acl.json (permissões), etc/menu.json, etc/router.json, Setup/ (migrações), GraphQl/ (a parte da API) e view/. Módulos próprios do cliente ficam em src/app/code/. Desligar um módulo em Lojas → Configurações → Módulos tira as telas e a API dele, sem apagar os dados.

2. Instalação e ambiente

2.1 Requisitos

  • PHP 8.1 ou superior com pdo_pgsql, mbstring, curl, gd, zip e openssl.
  • Composer. Bibliotecas: webonyx/graphql-php (API), symfony/mailer (e-mail), guzzlehttp/guzzle (Mercado Pago, Melhor Envio, Correios), openspout/openspout (Excel) e dompdf/dompdf (PDF dos relatórios).
  • PostgreSQL 15 (há um docker-compose.yml pronto para desenvolvimento, ouvindo só em 127.0.0.1:5432; em produção, PostgreSQL instalado no servidor ou gerenciado).
  • Para o backup: restic e o pg_dump/psql da mesma versão do PostgreSQL ou mais nova (postgresql-client-15).

2.4 Produção

  • Raiz web apontando para public/; tudo o mais fica fora do alcance do navegador. Todas as requisições vão para public/index.php (no Nginx: try_files $uri /index.php?$query_string;).
  • HTTPS obrigatório: o token da API vai no cabeçalho de cada requisição. Com o certificado instalado, ligue Configurações → Geral → Usar só HTTPS: páginas em http são redirecionadas, a API em http é recusada (403), o navegador recebe HSTS e o cookie do painel passa a ser Secure.
  • Atrás de um balanceador, proxy ou CDN, informe os IPs dele em Configurações → Geral → Proxies confiáveis. Sem isso, todos os clientes parecem vir do IP do proxy e o limite por IP bloqueia todo mundo junto; com isso, o IP do cliente e o HTTPS vêm de X-Forwarded-For e X-Forwarded-Proto (só quando enviados pelo proxy).
  • Crie uma chave em Sistema → Chaves da API para cada app e site, configure-os para enviá-la e ligue Exigir chave do aplicativo.
  • display_errors desligado no PHP; os erros vão para var/log.
  • var/ (logs, cache, sessões, e-mails) e public/media/ (imagens enviadas) graváveis pelo usuário do PHP; public/media/ entra no backup junto com o banco e o src/etc (3.5).
  • Backup: o cron do bin/backup.php ativo, um destino externo em Configurações → Backup e o kit de recuperação guardado fora do servidor (3.5).
  • Em CORS, informe só os sites que podem chamar a API pelo navegador.
  • src/etc/database.ini e mail.ini com permissão 600 (só o usuário do PHP lê), como o env.ini.
  • O painel já envia X-Frame-Options: DENY, CSP frame-ancestors 'none', nosniff e Referrer-Policy: same-origin. A sessão do painel termina depois de 8 h sem uso e 12 h desde o login (Configurações → Segurança do admin), e quando a senha muda. Sair é um POST com form_key (/admin/auth/logoutpost).

3.2 Webhook do Mercado Pago

A única rota fora do GraphQL e do painel: POST https://sua-loja/mercadopago/webhook. Cadastre-a no painel do Mercado Pago (Suas integrações → Webhooks, tópico Order) e copie a "assinatura secreta" para Configurações → Pagamento. Com a assinatura salva, avisos com x-signature inválida recebem 401, e também os assinados há mais de 10 minutos (o ts da assinatura, em segundos ou milissegundos): um aviso capturado e reenviado depois é recusado. O corpo do aviso só diz qual cobrança mudou: o sistema relê a cobrança na API do Mercado Pago, e o cron mercadopago-sync cobre os avisos perdidos.

3.3 Logs

  • var/log/iter-AAAA-MM-DD.log: erros e avisos do sistema, um arquivo por dia (inclui a causa real de um INTERNAL_ERROR da API). Consulta também em Sistema → Log do sistema.
  • Log de operações (tabela log_operation): quem fez o quê no painel ou pela API, com antes e depois, logins e exportações de relatórios de clientes e financeiros.
  • E-mails: tabela mail_queue, consultada em Sistema → E-mails enviados.

3.5 Backup

Módulo Iter_Backup, com restic. Cada cópia leva o banco em SQL puro (pg_dump --no-owner --no-privileges, em var/backup/dump/banco.sql, apagado depois), o commit.txt do código, public/media e src/etc. O restic compacta (zstd, nível máximo), cifra e só guarda o que mudou: com o banco de 17 MB e 4,5 MB de imagens, a primeira cópia ocupa 2,6 MB e cada nova cerca de 0,1 MB.

  • Configurações → Backup (system/backup/*, permissão Iter_Backup::backup): ligado, intervalo (1 h a 1 semana, com horário e dia), retenção (--keep-hourly/daily/weekly/monthly, padrão 24/7/4/12; todos em 0 é recusado), e-mail de falha, avisos no Dashboard (system/backup/dashboard_warnings; desligado, o Dashboard não mostra nada do backup) e destino: pasta local (padrão var/backup/repo, nunca em public/), Backblaze B2 (b2:<bucket>:iterstore) ou S3 compatível (s3:https://<endpoint>/<bucket>/iterstore). A chave secreta é gravada cifrada.
  • Senha do repositório: gerada no primeiro uso (64 hex), gravada cifrada em system/backup/repo_password. Credenciais vão ao restic pelo ambiente (RESTIC_PASSWORD, B2_ACCOUNT_*, AWS_*), a senha do banco por PGPASSWORD; nada vai na linha de comando.
  • Cron: a cada minuto, com flock. Copia quando vence o intervalo ou existe var/backup/run-now (botão "Fazer backup agora"). Depois de uma falha, espera 15 minutos. Limpeza (forget --prune) uma vez por dia; teste de restauração uma vez a cada 30 dias.
  • Situação: var/backup/status.json (última cópia, cópias, espaço, erro, teste), lido por Sistema → Backup e pelo Dashboard. O painel nunca chama o restic.
  • Teste de restauração: o banco.sql da última cópia é restaurado num banco <banco>_verify (o usuário do banco precisa de CREATEDB), conferido (todas as tabelas, e pedidos, clientes e produtos ao menos os contados antes do dump) e apagado.
  • Kit de recuperação (Sistema → Backup → Abrir o kit): só o perfil Administrador, pede a senha de novo, fica no log de operações (backup_kit). Mostra a senha do restic e a crypt_key do env.ini. Guardar no gerenciador de senhas da empresa e impresso, nunca por e-mail.
php bin/backup.php                    # o que o cron roda
php bin/backup.php now antes-migracao # uma cópia agora, com marcação
php bin/backup.php verify             # teste de restauração agora
php bin/backup.php zip [cópia]        # .zip de uma cópia (latest) em var/backup/, permissão 600

Restaurar num servidor novo

4. A API GraphQL

4.1 Endpoint e formato

Toda chamada é um POST para /core/graphql/index com um JSON {"query": "...", "variables": {...}}. A resposta é sempre HTTP 200 com data e/ou errors, exceto token ou chave inválidos (401), excesso de requisições (429) e chamada sem HTTPS com "Usar só HTTPS" ligado (403).

curl -s https://sua-loja/core/graphql/index \
  -H 'Content-Type: application/json' \
  -H 'X-Api-Key: itk_…'   # quando a chave é exigida \
  -d '{"query":"{ websites { id name isDefault } }"}'
[{"id": "15", "name": "Loja RJ", "isDefault": true}, {"id": "2238", "name": "Loja SC", "isDefault": false}]

Com variáveis (JavaScript)

const API = 'https://sua-loja/core/graphql/index';

async function gql(query, variables = {}, token = null) {
  const res = await fetch(API, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-Api-Key': process.env.API_KEY,   // Sistema → Chaves da API
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
    },
    body: JSON.stringify({ query, variables }),
  });
  const json = await res.json();
  if (json.errors?.length) {
    const err = new Error(json.errors[0].message);
    err.code = json.errors[0].extensions?.code;   // decida pelo código, não pela mensagem
    throw err;
  }
  return json.data;
}

const { product } = await gql(
  'query P($sku: String!) { product(sku: $sku) { name priceRange { min max } } }',
  { sku: 'MODA-CALCA-JEANS' },
);

Em PHP (Guzzle, já instalado no projeto)

$http = new GuzzleHttp\Client(['base_uri' => 'https://sua-loja/']);
$res = $http->post('core/graphql/index', [
    'headers' => ['Authorization' => 'Bearer ' . $token], // com o token de admin, a chave não é pedida
    'json' => [
        'query' => 'query ($s: OrderStatus) { orders(status: $s, pageSize: 50) { total items { number total } } }',
        'variables' => ['s' => 'processing'],
    ],
]);
$body = json_decode((string) $res->getBody(), true);
if (isset($body['errors'])) {
    throw new RuntimeException($body['errors'][0]['extensions']['code'] . ': ' . $body['errors'][0]['message']);
}

Para explorar a API, use Sistema → API (GraphiQL) no painel: autocompletar, documentação de cada campo e execução com a sessão do admin logado.

Com a chave exigida, o visitante e o cliente precisam dela (o login do admin também: generateAdminToken vai com a chave). Já com o token de admin em mãos, ou logado no painel (GraphiQL), a chave não é pedida. Uma chave por aplicativo: se uma vazar, revogue só ela e publique o app com a nova.

Um token de cliente nunca passa pelos campos do admin (a resposta é UNAUTHENTICATED). Um token inválido ou vencido é recusado com HTTP 401 e o código TOKEN_INVALID, mesmo em campos públicos: descarte-o e faça login de novo.

4.4 Erros

Todo erro traz extensions.code. A mensagem é em português e pode ser mostrada ao usuário, mas a lógica do cliente deve decidir pelo código. Exemplo, um produto com grade colocado no carrinho:

{
  "errors": [
    {
      "message": "'Calça Jeans Skinny' tem grade: escolha a variação (cor, tamanho...).",
      "path": [
        "addToCart"
      ],
      "extensions": {
        "code": "PRODUCT_IS_CONFIGURABLE"
      }
    }
  ]
}

Erros de sintaxe e de campo inexistente (testados no servidor):

{"errors":[{"message":"Syntax Error: Expected Name, found <EOF>","extensions":{"code":"GRAPHQL_PARSE_FAILED"}}]}
{"errors":[{"message":"Cannot query field \"slug\" on type \"Website\".","extensions":{"code":"GRAPHQL_VALIDATION_FAILED"}}]}

Token inválido (HTTP 401):

{"errors":[{"message":"Token inválido ou expirado. Faça login de novo.","extensions":{"code":"TOKEN_INVALID"}}]}

4.6 Envio de arquivos

uploadProductImage e setCategoryBanners recebem arquivos pelo GraphQL multipart request spec (multipart/form-data com operations, map e o arquivo). Exige o token do admin no cabeçalho: com só o cookie, o envio é recusado (proteção contra CSRF).

curl https://sua-loja/core/graphql/index \
  -H "Authorization: Bearer $TOKEN" \

6.2 Newsletter

Inscrição com confirmação por e-mail (double opt-in): subscribeNewsletter grava o e-mail como pendente e envia o e-mail com o link; o e-mail só passa a receber depois que a página do link chama confirmNewsletter com o token. Confirmado, ele entra nos envios de "Novidades" do Marketing; se for o e-mail de um cliente do website, o consentimento do cliente também é ligado.

  • subscribeNewsletter responde true sempre, mesmo para um e-mail já inscrito ou confirmado, para não revelar quem está cadastrado. Um segundo e-mail de confirmação para o mesmo endereço só sai depois de 1 minuto.
  • O link do e-mail sai de Configurações → Marketing → Newsletter → Link de confirmação na loja, com {token}; começando com /, vale o endereço da loja web que chamou (cabeçalho X-Store-Url, se estiver na lista de Configurações → Geral). Padrão: /newsletter/confirmar?token={token}. O link vale pelas horas configuradas (48 por padrão) e uma vez só.
  • Limite de inscrições por minuto por IP (5 por padrão): acima dele, TOO_MANY_REQUESTS.
  • Os inscritos ficam em Marketing → Inscritos (com exportação CSV).

payOrder cobra um pedido "Aguardando pagamento". No Pix, devolve o copia e cola (pixQrCode), a imagem (pixQrCodeBase64) e a validade; chamar de novo devolve o mesmo QR enquanto ele valer. No cartão, o app gera o token com o SDK MercadoPago.js V2 (a publicKey vem de mercadopagoSettings) e envia em card; recusado, pode tentar de novo com outro cartão. Este exemplo não foi executado aqui porque cria uma cobrança real no Mercado Pago.

  • card.paymentMethodId é o que o SDK devolveu em getInstallments. No débito, um cartão de débito vem como debvisa, debmaster, debelo… e é cobrado como debit_card em 1x; um pré-pago vem com a bandeira simples (elo, visa…) e é cobrado como prepaid_card, sem parcelas.
  • deviceId: o identificador do aparelho que o security.js do Mercado Pago gera (MP_DEVICE_SESSION_ID). Vai no cabeçalho X-meli-session-id e melhora a aprovação. Opcional.
  • Cada cobrança leva, além do valor: os itens (SKU, nome, opções, quantidade, preço e a "Categoria dos produtos" das Configurações), o frete como um item "Frete" (a soma dos itens precisa bater com o total; com desconto, o pedido vai como um item só), nome, CPF/CNPJ, e-mail, telefone e endereço do pagador, o "Nome na fatura do cartão" e, para cliente logado, a data do cadastro, se é a primeira compra e a data da última.
  • No app Jardim Vera, o SDK roda numa WebView invisível (react-native-webview): bandeira, parcelas, token e deviceId vêm do próprio MercadoPago.js. O número do cartão nunca passa pelo servidor da loja.
mutation {
  payOrder(number: "RJ000056", email: "maria@exemplo.com.br") {
    status statusLabel amount
    pixQrCode pixQrCodeBase64 expiresAt
    order { status statusLabel }
  }
}

# cartão
mutation ($card: MercadopagoCardInput!, $deviceId: String) {
  payOrder(number: "RJ000056", email: "maria@exemplo.com.br", card: $card, deviceId: $deviceId) {
    status statusDetail cardBrand cardNumber installments
    challengeUrl challengeCreq
    order { status }
  }
}
# variables: { "card": { "token": "<token do SDK>", "paymentMethodId": "visa", "installments": 3 }, "deviceId": "<MP_DEVICE_SESSION_ID>" }

A confirmação chega pelo webhook (e pelo cron de sincronização): o pedido passa para "Pagamento confirmado" (processing). O app consulta o pedido (guestOrder ou myOrder) para mostrar a situação.
